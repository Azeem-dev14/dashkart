# Multiplayer setup

Live 1v1 racing (`lib/features/multiplayer/`) runs on Firebase Realtime
Database. This is the record of what's provisioned and how to reproduce or
change it.

## What's live

| | |
|---|---|
| Firebase project | `dashkart-game` (console: https://console.firebase.google.com/project/dashkart-game/overview) |
| Realtime Database | `dashkart-game-default-rtdb`, `us-central1` |
| Registered apps | Android (`com.nammaflutter.dashkart`), iOS (`com.nammaflutter.dashkart`) |
| Config | `lib/firebase_options.dart`, `android/app/google-services.json`, `ios/Runner/GoogleService-Info.plist` — all generated by FlutterFire CLI, safe to regenerate, not secret (they identify the project, they don't authenticate to it) |
| Rules | `database.rules.json`, deployed via `firebase deploy --only database` |

`main.dart` checks `DefaultFirebaseOptions.currentPlatform.apiKey != 'REPLACE_ME'`
to decide whether to call `Firebase.initializeApp`. That's now real, so
multiplayer is live on every build — no per-build flag to flip.

## Database shape

```
rooms/
  {5-char code}/
    trackId: string
    status: "lobby" | "racing"
    createdAt: server timestamp
    players/
      host/  { name, kartId, ready, progress, lateral, finished }
      guest/ { name, kartId, ready, progress, lateral, finished }
```

One node per room, ~10 Hz telemetry writes per racer while racing — small,
high-churn key/value data, which is what RTDB (not Firestore) is built for.

## Web controller (phone as gamepad)

On web the first screen after loading is a QR code (`lib/features/gamepad/`).
A phone that scans it opens the same web app at `/?pad=CODE`, which renders
only a touch controller and writes its input to `pads/{code}`:

```
pads/{5-char code}/
  connected: bool      phone attached (reset by the phone's onDisconnect)
  steer: -1..1, brake: bool, drift: bool
  item, pause: int     press counters — a bump is one press
```

The race reads that node instead of the on-screen buttons. Three one-off
steps are needed before it works on a deployed build:

1. Register a web app and put its config into `DefaultFirebaseOptions.web`
   (`firebase apps:create web DashKart --project dashkart-game`, then
   `firebase apps:sdkconfig web <appId>`, or re-run `flutterfire configure`
   with `web` in `--platforms`).
2. Deploy the rules (the `pads` node was added): `firebase deploy --only database`.
3. Host the build somewhere the phone can reach (`flutter build web`, then
   Firebase Hosting or any static host). The QR link follows wherever the game
   was loaded from; override with `--dart-define=PAD_BASE_URL=<url>` (needed
   for local dev, since a phone can't reach `localhost` — use the LAN IP).

## Rules — the trade-off

```json
{
  "rules": {
    "rooms": { ".read": true, ".write": true },
    ".read": false,
    ".write": false
  }
}
```

`/rooms` is open, no auth, world-readable and world-writable. That's a
deliberate call for a community demo with no login system, not a production
posture: anyone with the database URL can read or overwrite any room. Two
things bound the actual risk — the client only ever writes to its own
`players/{host|guest}` slot in practice, and rooms are ephemeral (nobody
persists them or relies on their contents past one race). Before this ships
somewhere that matters, put real auth (even anonymous auth) behind these
rules and scope writes to `auth.uid`.

Redeploy after editing `database.rules.json`:

```sh
firebase deploy --only database --project dashkart-game
```

## Reproducing this from scratch

```sh
firebase login
firebase projects:create <project-id> --display-name "DashKart"
firebase init database --project <project-id>   # creates the default RTDB instance
firebase deploy --only database --project <project-id>
flutterfire configure -p <project-id> --platforms=android,ios -y
```

`flutterfire configure` overwrites `lib/firebase_options.dart` and drops
`google-services.json` / `GoogleService-Info.plist` into place; nothing in
either needs hand-editing.

## Known gaps

- **No auth.** See the rules trade-off above.
- Two orphaned Firebase apps (Android + iOS) remain registered under the old
  placeholder ID `com.example.dashkart` from before the app was renamed to
  `com.nammaflutter.dashkart`. Harmless — unreferenced by any config file —
  but can be removed from the console (Project settings ▸ Your apps) if the
  clutter bothers you; the CLI has no delete command for this.
- Changing the Android `applicationId` or iOS bundle ID again means
  re-running `flutterfire configure -p dashkart-game --android-package-name=<new> --ios-bundle-id=<new> -y`
  to register a new app under the new ID — the old config won't follow a
  rename automatically.
- **No room cleanup job.** Abandoned rooms (both `onDisconnect` slots empty)
  stay in the database indefinitely. Harmless at demo scale; add a Cloud
  Function or scheduled cleanup if room count ever matters.
